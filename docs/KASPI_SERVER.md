# Серверное подключение Kaspi без Android

Режим `kaspi` использует протокол из tapter-dev/kaspi-pos-automation, commit
175577e (MIT, копия лицензии: `src/kaspi/LICENSE.tapter`). Это сторонняя реализация
мобильного протокола, не подтверждённая официальная интеграция Kaspi.
Android, Appium и эмулятор для этого режима не нужны.

## Локальная подготовка

Нужен Node.js >=24. Из корня репозитория:

```sh
npm ci
npm run init:kaspi
npm run check
npm test
npm run test:http
npm run start:kaspi
```

Инициализация сохраняет `.env.kaspi` с правами 600 и независимыми случайными
`ADMIN_PASSWORD` / `ENCRYPTION_KEY`, не печатает их и не меняет существующий файл.
База находится в `data-kaspi/`, отдельно от sandbox. Порт по умолчанию 3081.
Проверка работоспособности: `GET /healthz` → 200, `{"ok":true}`.
Файл, ключ и базу сохраняйте вместе; не отправляйте их в Git или журналы.
Не запускайте два процесса с одним DATA_DIR. Не переключайте существующую
sandbox/Android-базу на другой драйвер.

Реальные операции по умолчанию выключены (`LIVE_AUTOMATION_ENABLED=false`).
SMS-вход доступен отдельно от отправки платежей, чтобы сначала проверить
подключение. Для удалённого доступа необходимы HTTPS, корректный PUBLIC_BASE_URL
и приватный доступ к кабинету. Не публикуйте dev-сервер напрямую.

## Подключение кассира

Исходящие HTTPS-домены: `entrance-pay.kaspi.kz`, `mtoken.kaspi.kz`, `qrpay.kaspi.kz`.
Коннектор использует HTTP(S)_PROXY / NO_PROXY через EnvHttpProxyAgent с проверкой
TLS и таймаутом 15 секунд. Перенаправления запрещены. Сетевые разрешения должны
быть применены к среде до попытки входа.

Войдите в операторскую панель с локальным ADMIN_PASSWORD. Создайте компанию,
указав в «Кабинет кассира» точное название организации из Kaspi. На вкладке компаний
нажмите «Подключение», введите телефон кассира и полученный SMS-код.
Код отправляется только при явной отправке формы; в чат его вводить не нужно.
Банковские токены не возвращаются в браузер. Сессия и ключ устройства шифруются
AES-GCM с привязкой к UUID компании в таблице `kaspi_accounts`.

Серверные admin-endpoints (только с HttpOnly cookie оператора и проверкой Origin):

- `POST /admin/kaspi/:id/start`, тело `{"phone":"+77001234567"}` → `{"sms_sent":true}`.
- `POST /admin/kaspi/:id/verify`, тело `{"otp":"123456"}` → `{"connected":true}`.
- Отключение через существующий `POST /admin/merchants/:id/disconnect` удаляет
  локальную банковскую сессию, сохраняет ключ устройства; отзыв на стороне Kaspi
  этим действием не гарантирован.

Незавершённый вход живёт в памяти пять минут, допускает до пяти попыток кода.
Перезапуск требует нового SMS-входа, если предыдущий не был завершён.
При открытых платежах повторный вход разрешён только в исходный ProfileId; один ProfileId нельзя подключить
к двум компаниям. При смене организации или истечении сессии операции блокируются.
Версии клиента из upstream могут устареть: APP_VERSION / APP_BUILD и другие APP_*
можно задать в `.env.kaspi`; текущая совместимость с Kaspi не подтверждена.

## Проверка перед реальными операциями

Локальные тесты проверяют имитированные ответы: SMS/ECDH, шифрование сессии,
права оператора, QR, потерю соединения, повтор запроса и сверку. Они не подтверждают
приём запросов банком. Внешних запросов в Kaspi при автоматических тестах нет.

Создание счёта выполняется единожды после сохранения durable submit marker.
При ошибке после этого момента состояние становится `unknown`, повторное создание
запрещено. Полученный QrOperationId сохраняется до формирования QR. QR генерируется
локально из исходной ссылки Kaspi, без внешних генераторов. Возвраты не подключены.

Сверка намеренно строгая: ответ должен содержать QrOperationId, Amount, Currency,
ProfileId, а для счёта по телефону также Comment с UUID нашего счёта. Статус
Processed подтверждает оплату только при совпадении всех этих полей. Состав реальных
ответов upstream не гарантирует. Если поля отсутствуют или отличаются, результат
остаётся `unknown`; для ввода в эксплуатацию потребуется проверить реальные ответы
и при необходимости доработать сверку по надёжным данным истории. Не ослабляйте
проверку до одного Status. Новый статус также требует сверки, а не означает отказ.

После проверки входа и согласования контролируемого теста можно явно включить
LIVE_AUTOMATION_ENABLED=true и перезапустить сервер. До проверки полного цикла
на своём кабинете этот коннектор не предназначен для реальных заказов.
