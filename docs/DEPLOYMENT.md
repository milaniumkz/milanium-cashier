# Развёртывание MBusiness на собственном сервере

Пока подготовлена и проверена среда разработки. Выполнить внешний deployment
нужно после получения сервера и домена. Публичное развёртывание ещё не выполнено.

## Требования

Linux, Node.js >=24 (встроенный node:sqlite), npm, локальный диск для SQLite,
HTTPS reverse proxy (например, Nginx), один процесс API/worker на одну базу.
Android для режима kaspi не нужен. Не используйте сетевой диск и несколько реплик.

1. Перенесите исходники и lockfile на сервер под отдельного сервисного пользователя.
2. В корне проекта выполните `npm ci --omit=dev`.
3. Для sandbox выполните `npm run init`; для прямого коннектора — `npm run init:kaspi`.
4. Сохраните сгенерированный конфигурационный файл с правами 600, ключ шифрования
   вместе с резервными копиями данных. Не выводите секреты в CI, логи и чат.
5. В выбранном env-файле установите NODE_ENV=production, HOST=127.0.0.1,
   PUBLIC_BASE_URL=https://ВАШ_ДОМЕН и абсолютный DATA_DIR. Production не допускает
   sandbox: для тестового окружения оставьте NODE_ENV=development и изолируйте доступ.
6. Для режима kaspi оставьте LIVE_AUTOMATION_ENABLED=false до проверки входа и
   надёжной сверки реальных ответов по `docs/KASPI_SERVER.md`.
7. Разрешите исходящие HTTPS entrance-pay.kaspi.kz, mtoken.kaspi.kz, qrpay.kaspi.kz.
   При использовании прокси сохраните доверенную CA и TLS verification.
8. WEBHOOK_ALLOWED_ORIGINS — точные HTTPS origins серверов клиентов через запятую.
   Домен, который не разрешён, нельзя сохранить из кабинета. Приватные адреса запрещены.
9. При Nginx на том же сервере установите TRUSTED_PROXY_IPS=127.0.0.1. Укажите
   точный адрес непосредственного proxy peer, не адрес клиента и не подсеть.
   Без этого API увидит IP прокси и отклонит запрос компании.
10. Запускайте `npm run start:kaspi` (env-файл .env.kaspi) через systemd или иной
   supervisor из корня проекта. Sandbox использует `npm start` и .env.

База требует постоянного DATA_DIR. Начальные ADMIN_PASSWORD и ENCRYPTION_KEY
генерируются случайно: не используйте демонстрационные значения.
Проверяйте `/healthz`, реальный вход пользователя и каталог записи базы после запуска.
Панель компаний: `/`, документация: `/docs`, администратор: `/operator`.

## Пример reverse proxy

Подставьте домен, сертификат и тот порт, который реально указан в env-файле.
Для .env.kaspi по умолчанию 3081, для .env — 3080.

```nginx
server {
    listen 443 ssl;
    server_name payments.example.kz;
    ssl_certificate /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;
    location / {
        proxy_pass http://127.0.0.1:3081;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_read_timeout 60s;
    }
}
```

Проверка API использует socket.remoteAddress. Только для точных адресов
TRUSTED_PROXY_IPS она принимает единственное значение X-Forwarded-For.
Заголовок с цепочкой адресов, отсутствующий или некорректный заголовок от
доверенного прокси приводит к отказу API. Конфигурация выше заменяет заголовок
значением $remote_addr; не используйте $proxy_add_x_forwarded_for для этого пути.
Многоуровневые proxy/CDN требуют отдельной настройки авторитетного клиентского IP.

Fastify по умолчанию не доверяет X-Forwarded-For: не включайте trustProxy=true
без точной настройки доверенного proxy hop. После развёртывания настройте
ограничение частоты на Nginx, чтобы ограничение по IP не объединяло всех клиентов
за одним reverse proxy. Cookie Secure определяется NODE_ENV=production.
Перенаправьте HTTP на HTTPS. Закройте прямой внешний доступ к порту Node.
Ограничьте административный `/operator` и `/admin/*` доверенными IP/VPN на proxy.

## Деньги и эксплуатация

Настройте процесс получения оплаты за подписку и выдайте администратору доступ
для проверки переводов. Компания может создать заявку, но без подтверждённого
перевода никакое зачисление не произойдёт. Эквайринг автоматически не подключён.
Перед коммерческим запуском подтвердите выбранную схему: месячная подписка
заменяет 200 ₸ за отдельный счёт.

Делайте согласованные резервные копии SQLite вместе с ENCRYPTION_KEY. При копии
файла остановите процесс и учитывайте WAL, либо используйте SQLite backup API.
Проверяйте восстановление на отдельном каталоге данных. Не меняйте ключ
шифрования для существующей базы. При обновлении заранее сохраните backup,
затем остановите старый процесс, обновите зависимости и запустите один новый.

SMTP, сброс пароля по email, приглашение команды и автоматический эквайринг
не подключены. Локальные тесты не подтверждают банковскую совместимость.
