# Привязка к реальному Android UI

`src/drivers/android.js` управляет установленным приложением через стандартный W3C / Appium протокол. Он не обращается к выдуманным Kaspi API. JSON-конфигурация — проверяемый набор шагов для **конкретной версии** приложения, языка и роли кассира.

## Получение селекторов

1. Установите приложение и проверьте вход на выделенном устройстве.
2. Запишите версию APK, Android, язык, модель устройства, роль кассира и доступные функции.
3. При остановленном API используйте Appium Inspector или `npm run android -- inspect MERCHANT_UUID`. Для `inspect` уже должны быть указаны package/activity. XML сохранится в `DATA_DIR/inspection`; он может содержать персональные сведения, поэтому не коммитьте его.
4. Выберите точные `resource-id` или accessibility id. XPath применяйте только к однозначному элементу. Драйвер отклоняет несколько видимых совпадений.

Формат селектора:

```json
{"using":"id","value":"OBSERVED_PACKAGE:id/OBSERVED_ID"}
```

Это пример формы, а не настоящий селектор Kaspi. Разрешены `id`, `accessibility id`, `xpath`. Каждый шаг навигации — `click` / `wait` с `selector` или `{"action":"back"}`. `home` должен детерминированно возвращать из поддерживаемых экранов к экрану проверки компании. Неподходящий универсальный набор Back-нажатий может разлогинить приложение; проверяйте реальные переходы.

## Контракт конфигурации

| Поле | Что должно быть подтверждено на устройстве |
| --- | --- |
| `ready` | Уникальный признак авторизованного экрана |
| `account` | Точное название/идентификатор, совпадающий с `account_label` компании в сервисе |
| `phone.navigation` | Путь к форме удалённого счёта |
| `phone.phone` | Редактируемое поле номера; драйвер проверяет введённый `+7…` |
| `amount` | Поле суммы в целых тенге; проверяется после ввода |
| `reference` | Поле для внутреннего UUID счёта, сохраняющееся в банковской операции |
| `description` | Необязательное отдельное поле описания; не должно затирать reference |
| `submit` | Точная кнопка финальной отправки/создания |
| `result`, `provider_id` | Признак результата и стабильный ID созданной операции |
| `qr.qr` | Элемент с QR, из которого действительно получается читаемый PNG |
| `qr.link` | Необязательный элемент с полной HTTPS-ссылкой банка |
| `qr.live_status` | Статус и реквизиты операции на том же экране, без выхода из активного QR |
| `history` | Поиск существующего счёта по его банковскому ID и открытие деталей |
| `history.details` | ID, сумма, валюта, reference, статус и точное соответствие четырём состояниям |
| `payment_origins` | Реально наблюдаемые HTTPS origins внутри `kaspi.kz`; полный путь сюда не входит |

**Универсальность этого контракта для Kaspi Pay ещё не доказана.** Если приложение не позволяет сохранить reference, получить устойчивый ID, читать детали/статусы или генерировать QR на заданную сумму, одних селекторов недостаточно: потребуется изменить адаптер под подтверждённый способ корреляции либо отключить соответствующий метод. Сопоставление только по одинаковой сумме не подходит. Нельзя просто убрать проверки из `evidence()`.

Текущий адаптер сравнивает сумму как целое число после удаления пробелов, валюту с `KZT`, reference — с UUID сервиса. Если UI показывает суффикс валюты, дробную часть, форматированный номер или иной текст, потребуется явный нормализатор для наблюдаемого формата и тесты с реальными обезличенными примерами. Незнакомый формат приводит к ошибке, а не к подтверждению оплаты.

В примере `config/android.kaspi.example.json` намеренно оставлены пустые значения и `verified: false`. Они блокируют реальные операции. Для поддержки только счетов по телефону удалите весь блок `qr`; для QR без счетов — весь блок `phone`. Оставшийся метод и `history` должны быть полностью настроены. Строки статусов берутся из настоящего приложения, а не из тестовых значений `PAID`/`PENDING`.

## QR и ссылка

Сервис вводит сумму в приложение, создаёт операцию и снимает изображение соответствующего QR-элемента. `jsQR` проверяет, что в PNG есть читаемый код. Если его содержимое — HTTPS-ссылка с разрешённым origin, она возвращается без добавления параметров суммы. Для других payload возвращается только изображение. QR без доступного кода, защищённый/чёрный снимок или неподтверждённый способ привязки суммы не заменяются искусственным QR.

Один активный QR резервирует Android компании. Уход в историю, ручной режим или перезапуск могут сделать изображение неактуальным. Поэтому при ручном режиме/перезапуске сервис скрывает QR и сверяет исходную операцию через историю. Он не создаёт новый платёж автоматически.

## Порядок испытания реальной интеграции

После настройки сценариев используйте свою компанию и заказ с известными реквизитами:

1. Проверьте совпадение компании, номера, суммы и reference **до отправки**.
2. Убедитесь, что одно нажатие даёт ровно одну банковскую операцию.
3. Повторите API-запрос с тем же телом и ключом: банковский счёт должен остаться один.
4. Проверьте подтверждение, отказ и окончание срока; сравните ID, сумму и статус с приложением кассира.
5. Для QR проверьте декодированную ссылку и сумму на стороне плательщика.
6. Оборвите связь после отправки; сервис должен перейти в `unknown` и сверять существующую операцию, не отправляя её заново.
7. Проверьте переавторизацию и полный перезапуск сервера/Android.

Реальный платёж на этом этапе инициирует владелец тестового аккаунта. Автоматические тесты проекта не проводят банковских операций. Обновления APK сначала проверяйте на отдельной конфигурации; при несовпадении UI остановите автоматизацию.
