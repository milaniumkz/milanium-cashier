# MBusiness: кабинеты компаний и биллинг

## Маршруты

- `/` — новый адаптивный интерфейс MBusiness.
- `/docs` — публичная документация API, примеры cURL / Node.js / Python и проверка webhook.
- `/operator` — существующая панель администратора с дополнительным разделом баланса и заявок.
- `/auth/register`, `/auth/login`, `/auth/logout` — регистрация компании и сессия владельца.
- `/account/*` — только компания из серверной сессии. UUID компании от клиента не принимается.
- `/v1/*` — Bearer API существующего сервиса. Новый `/v1/billing` возвращает тариф и остаток лимита.

Регистрация принимает `{company, login, password}`. Логин регистронезависим,
3–100 символов; пароль 12–128 символов. Логин может быть почтой, но почта
не проверяется и не используется для восстановления. В ответе регистрации
выдаются одноразовые API-ключ и секрет webhook. Потерянный ключ можно заменить
в кабинете. Потерянный пароль пока требует помощи администратора, автоматическая
отправка писем восстановления не подключена. Один владелец на одну компанию.

Пароли хешируются scrypt со случайной солью; проверка постоянного времени.
Cookie mb_session — HttpOnly, SameSite=Strict, Secure в production. В базе
хранятся только хеши токенов, срок 12 часов. Сессии переживают перезапуск сервиса.
Выход удаляет текущую сессию; смена пароля отзывает все предыдущие сессии.
Глобальная защита Origin и отдельные rate limits применяются к формам входа.
Все данные компании, платежи, webhook, деньги, кассир и API-ключи выбираются
только через merchant_id из серверной сессии.

## Подписки

Последняя тарифная сетка реализована как месячная подписка ВМЕСТО платы 200 ₸
за счёт. Это допущение явно обозначено в интерфейсе; окончательно подтвердите
бизнес-правило до коммерческого запуска.

Старт: 50 счетов/день, 10 000 ₸/месяц. Бизнес: 200 и 25 000 ₸.
Про: 400 и 60 000 ₸. Про Макс: 700 и 90 000 ₸.
Тариф оплачивается с баланса. Продление того же активного тарифа добавляет
календарный месяц к текущему сроку; день месяца обрезается до последнего
существующего дня. Смена тарифа активирует месяц с текущего момента по полной
цене без компенсации остатка; интерфейс явно предупреждает перед оплатой.
Автопродления нет. Даты окончания хранятся в UTC, показываются по Алматы.

Больше 700: компания оставляет запрос с объёмом и контактом. Администратор видит
его в `/operator` → «Баланс и заявки» и предлагает дневной лимит / месячную цену.
Предложение появляется в тарифах компании и оплачивается с её баланса.
Менять условия уже действующей индивидуальной подписки до её окончания нельзя.

Баланс хранится в целых тенге. Деньги не увеличиваются от действий пользователя:
заявка POST /account/topups лишь создаёт pending. Администратор проверяет
реальное поступление, затем через POST /admin/topups/:id/review с решением
approved и bank_reference зачисляет сумму. Один банковский идентификатор нельзя
повторно использовать даже для другой компании. Повторное подтверждение того же
платежа не увеличивает баланс. Отклонённая заявка не создаёт начисления.
Банковские реквизиты для приёма оплаты пока предоставляются администратором
вручную; автоматический эквайринг отсутствует.

Операции по балансу и оплата подписки записываются в business_ledger атомарно
в транзакциях SQLite, без отрицательного баланса. Повторные заявки и покупки
защищены Idempotency-Key. Повтор с изменёнными условиями возвращает конфликт.

Дневные лимиты считаются по Asia/Almaty. Место резервируется при создании
новой записи invoices в той же BEGIN IMMEDIATE транзакции, что и счёт.
50 параллельных разрешённых запросов на Старт занимают все 50 мест; 51-й
отклоняется. Idempotent replay остаётся доступен даже после окончания подписки.
Подтверждённая ошибка до submit возвращает место; safe retry проверяет подписку
и резервирует место заново. Неоднозначная отправка сохраняет место до сверки.
История, проверка статусов, webhook и выдача уже созданных счетов не блокируются
из-за истечения подписки или исчерпания лимита. Принятые в очередь задания
сохраняют выделенное место после окончания периода.

## Совместимость с существующими данными

Миграции только добавляют новые таблицы business_*. Старые компании,
созданные оператором или CLI до регистрации SaaS, не получают автоматически
владельцев, подписку и требования нового биллинга. Они остаются в операторском
контуре для совместимости. Новые публично зарегистрированные компании
всегда управляются биллингом; admin API создания счетов для них не обходит лимиты.
Перенос старой компании в самостоятельный кабинет требует отдельной миграции
с проверкой владельца. Нельзя создавать второй кабинет для обхода сверки платежей.

Банковская сессия Kaspi по-прежнему хранится отдельно и шифруется с привязкой
к компании. Работа прямого коннектора с реальным Kaspi не подтверждена.
Никакие тесты регистрации, подписки или sandbox не доказывают доступность банка.

## Проверки

`npm run check`, `npm test`, `npm run test:http`.
`npm run test:browser` запускает изолированный временный сервер и свежий профиль
Chromium, регистрирует фиктивную компанию через UI, подтверждает тестовое
пополнение через UI администратора, покупает подписку, создаёт счёт, получает QR,
имитирует оплату и проверяет подтверждение. Проверяет настройки, документацию,
мобильный вход/выход и отсутствие ошибок JS/загрузки ресурсов.
Ни реальные деньги, ни банковские SMS при этом не используются.

## Привязка ключа к серверу

Все ключи, включая существующие операторские компании, требуют привязки к
одному публичному исходящему IP до доступа к любому `/v1/*`. Непривязанные
существующие ключи после обновления возвращают API_SERVER_REQUIRED (403).
Администратор может задать адрес через карточку компании в `/operator`.
Владелец задаёт IP с подтверждением пароля в «API и webhooks».
`POST /account/api-server` принимает `{ip,password}` и возвращает
`{api_key,api_ip}`. IP и хеш нового ключа сохраняются атомарно с аудитом;
предыдущий ключ отключается. API-ключ не даёт доступа к смене привязки.
Пользователь другой компании не может изменить чужой IP.

IP проверяется централизованно для всего `/v1/*`, в том числе `/v1/billing`.
Публичная страница оплаты и кабинет компании по cookie не ограничиваются IP.
Поддерживаются точные IPv4/IPv6 с канонизацией IPv4-mapped socket addresses.
Подсети, wildcard, домены, URL, порты, приватные и служебные адреса не принимаются.
За одним публичным NAT/proxy могут быть несколько серверов: IP-привязка их
не различает и не является доказательством физической уникальности машины.

Подробное руководство клиенту: `/docs#server` и `docs/INTEGRATION.md`.
Настройка доверенного reverse proxy: `docs/DEPLOYMENT.md`.
