# HTTP API v1

Все API-запросы выполняются с backend вашего приложения. JSON, UTF-8. Сумма — **целые тенге**, `currency: KZT`. `15000` означает 15 000 ₸. Текущий технический диапазон 1–99 999 999 не заменяет лимиты конкретного приложения/аккаунта.

## Авторизация

`Authorization: Bearer <API-ключ компании>`. Ключ выдаётся в кабинете при создании компании. На уровне API компания определяется по ключу; поле `merchant_id` в запросе создания запрещено. Доступ к счёту другой компании возвращает 404.

## Создать счёт

`POST /v1/invoices`, заголовок `Idempotency-Key`: 8–120 символов `[A-Za-z0-9_.:-]`.

```json
{
  "order_id": "order-1001",
  "amount": 15000,
  "currency": "KZT",
  "method": "phone",
  "customer_phone": "+77001234567",
  "description": "Заказ 1001"
}
```

Для QR укажите `"method": "qr"` и уберите `customer_phone`. Номер обязателен только для `phone`; формат `+7` и 10 цифр. Пустой `description` допустим. Не передавайте в описание секреты или лишние персональные данные.

Успех: 201 для новой задачи, 200 для точного повтора. Ответ до выполнения Android-сценария:

```json
{
  "id": "UUID",
  "order_id": "order-1001",
  "merchant_id": "MERCHANT_UUID",
  "amount": 15000,
  "currency": "KZT",
  "method": "phone",
  "status": "queued",
  "error_code": null,
  "provider_id": null,
  "checkout_url": "https://your-cashier.example/p/RANDOM_TOKEN",
  "payment_url": null,
  "qr_available": false,
  "expires_at": null,
  "created_at": 1790208000000,
  "updated_at": 1790208000000,
  "replay": false
}
```

Это иллюстрация схемы, не действительный банковский счёт. `checkout_url` можно открыть сразу: страница обновляет статус и покажет QR/ссылку после получения. `payment_url` может оставаться `null`, если приложение не выдало подходящую ссылку. Ни адрес магазина с добавленным `amount`, ни заранее нарисованный QR не создаются.

Повтор после сетевой ошибки отправляйте с **тем же** `order_id`, телом и `Idempotency-Key`. Изменённый запрос или иной ключ для уже существующего заказа дают 409. Новый ключ/заказ нельзя использовать для автоматического обхода `unknown`: сначала нужно найти исходную банковскую операцию.

## Прочитать состояние

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | `/v1/invoices/:id` | Текущее состояние счёта |
| GET | `/v1/invoices` | `{data: [...]}`, последние 100 счетов компании |
| GET | `/v1/capabilities` | Доступные методы, режим, состояние подключения |
| GET | `/healthz` | Жив ли HTTP-сервис; не подтверждает доступность Kaspi |

Временные значения объекта счёта — Unix milliseconds. В Android-режиме `expires_at` сейчас `null`, пока адаптер не настроен на чтение срока из реального UI. Конечный статус определяется состоянием операции в приложении.

| Статус | Действие вашего backend |
| --- | --- |
| `queued`, `processing` | Подождать; операция ещё создаётся |
| `pending` | Показать клиенту оплату, ждать результата |
| `paid` | Сверить компанию, заказ, сумму/валюту; исполнить заказ один раз |
| `declined`, `expired` | Показать соответствующий результат |
| `requires_auth` | Кассиру нужен повторный вход; задача не отправлена |
| `failed` | Ошибка до отправки; оператор может разрешить повтор |
| `unknown` | Исход не определён; сверять существующую операцию, не повторять отправку |

Ошибки имеют форму `{ "error": { "code": "...", "message": "..." } }`. Основные HTTP-коды: 400 — поля/ключ идемпотентности, 401 — авторизация, 404 — объект не найден, 409 — конфликт/кассир не подключён/метод недоступен, 429 — частые запросы.

## Webhook

Добавьте origin вашего backend в `WEBHOOK_ALLOWED_ORIGINS`, например `https://api.your-app.example`, перезапустите сервис и сохраните полный URL webhook в карточке компании. Разрешены публичные HTTPS-адреса; локальные/частные сети и redirects отвергаются.

```json
{
  "event_id": "EVENT_UUID",
  "type": "invoice.paid",
  "created_at": "2026-09-24T00:00:00.000Z",
  "invoice": { "id": "INVOICE_UUID", "status": "paid" }
}
```

`invoice` в настоящем событии содержит полный объект счёта из API. `created_at` самого события — ISO 8601. Подпись: HMAC-SHA256 от `timestamp + "." + rawBody`, секрет — индивидуальный `webhook_secret`. Заголовки:

- `X-Cashier-Timestamp`: Unix seconds;
- `X-Cashier-Signature`: `v1=<hex>`;
- `X-Cashier-Event`: `event_id`.

Готовая проверка — `examples/verify-webhook.mjs`. Проверяйте исходные байты **до** преобразования JSON; окно timestamp — 5 минут. Доставка повторяется до 12 раз с задержкой; успешный ответ — HTTP 2xx. `event_id` остаётся тем же при повторе, timestamp подписи обновляется.

На backend используйте транзакцию и UNIQUE по event_id, сверяйте заказ/компанию/сумму/валюту и актуальный GET счёта. События могут приходить повторно и не по порядку: позднее `pending` не должно отменить уже подтверждённый заказ. Webhook не содержит номера плательщика.

## Android в кабинете оператора

Эти маршруты требуют операторской HttpOnly-cookie, полученной через `POST /admin/login`. Они не предназначены для мобильного приложения покупателя.

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/admin/android/:merchantId/manual` | Приостановить очередь, перейти к устройству |
| GET | `/admin/android/:merchantId/screen` | PNG текущего экрана, только ручной режим |
| POST | `/admin/android/:merchantId/input` | `{action: "tap", x, y}`, `{action: "text", text}` или `{action: "back"}` |
| POST | `/admin/android/:merchantId/resume` | Проверить кассира и возобновить автоматизацию |

Ввод не записывается в журнал сервиса. Ручное управление и автоматические действия не должны выполняться одновременно. UI сервисного кабинета обеспечивает этот порядок. Не публикуйте управляющие Android-маршруты отдельно от администраторской авторизации.

## Мобильные приложения

Общий контракт одинаков для Flutter, React Native, Kotlin, Swift: ваш backend создаёт счёт и возвращает `checkout_url`; приложение открывает её внешним браузером. Секрет компании остаётся на сервере. Для отображения QR на собственном экране используйте данные своей серверной прослойки или страницу оплаты. Пример Flutter — `examples/flutter_checkout.dart`; зависимости и маршрут backend настраиваются в вашем приложении.
