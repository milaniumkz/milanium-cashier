# MBusiness: как подключить оплату к вашей системе

Интеграция выполняется на backend вашей CRM, магазина или приложения.
API-ключ не передаётся покупателю и не размещается в браузере или мобильном APK.
Счета создаёт ваш сервер; покупателю нужна только публичная ссылка на оплату.

## 1. Подготовьте кабинет компании

1. Зарегистрируйте компанию в MBusiness: название, логин и пароль.
2. Сохраните секрет webhook, показанный при регистрации.
3. Откройте «Интеграция → 1Kaspi → Тариф» и выберите тариф.
4. Оплатите месячный тариф через QR, ссылку Kaspi или удалённый счёт. Подписка активируется после серверного подтверждения оплаты. Дополнительных 200 ₸ за счёт нет.
5. Подключите кассира через SMS-форму в кабинете. Для sandbox этого не требуется.

## 2. Привяжите сервер и получите ключ

Узнайте постоянный публичный **исходящий** IP backend-сервера. Адрес домена,
локальный IP контейнера и IP посетителя сайта для этого не подходят. При NAT
нужен IP выходного шлюза. В облаке настройте статический исходящий адрес.

В разделе «Интеграция → 1Kaspi → API и webhooks» заполните «Сервер интеграции»: один IPv4 или IPv6
без URL, порта и маски. Подтвердите пароль MBusiness. Сохраните новый API-ключ
в защищённой конфигурации backend. Старый ключ, в том числе регистрационный,
сразу перестанет работать. Ротация ключа без смены сервера сохраняет привязку.

Повторите привязку при смене IP. Нельзя привязать подсеть, несколько адресов,
wildcard или динамический DNS. Если сервер использует и IPv4, и IPv6, настройте
постоянный протокол / адрес выхода. Проверяется один точный IP.

Проверка с вашего backend, без необходимости создавать платёж:

```sh
curl https://YOUR_MBUSINESS_SERVER/v1/capabilities \
  -H 'Authorization: Bearer YOUR_API_KEY'
```

Ответ 200 содержит api_server_ip. Это проверка API-доступа, а не готовности
банковского кассира. При 403 API_SERVER_REQUIRED настройте привязку и используйте
новый ключ. При 403 API_IP_NOT_ALLOWED проверьте реальный IP выхода сервера / NAT.
Не пытайтесь подставлять адрес через X-Forwarded-For или X-Real-IP.

IP-привязка не отличает несколько машин за одним NAT или общим прокси.
Она ограничивает адрес использования ключа, но не доказывает количество
физических серверов и не заменяет хранение ключа в секрете.

## 3. Создайте счёт из вашей системы

Получите сумму заказа из своей доверенной базы, не из входных данных покупателя.
Сохраните стабильный order_id и Idempotency-Key для этой попытки оплаты.
Один и тот же заказ нельзя автоматически повторять с новыми ключами при таймауте.

```sh
curl -X POST https://YOUR_MBUSINESS_SERVER/v1/invoices \
  -H 'Authorization: Bearer YOUR_API_KEY' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: order-1001-attempt-1' \
  -d '{"order_id":"order-1001","amount":15000,"currency":"KZT","method":"qr"}'
```

amount — целое число **тенге**, не тиынов. Для счёта по телефону используйте
method=phone и customer_phone в формате +77001234567.
Список полей и примеры Node.js/Python: `/docs#create`, `/docs#quickstart`.

Сохраните полученный id в записи заказа и передайте checkout_url покупателю:
редиректом в браузере, кнопкой «Оплатить» или сообщением. На странице появится QR
или доступная ссылка Kaspi. Для просмотра публичной страницы ключ не нужен,
и IP покупателя не ограничивается. Создание асинхронное: первый ответ queued
не означает готовый QR и не подтверждает оплату.

## 4. Получите подтверждение

Настройте HTTPS webhook своего backend в «API и webhooks». Origin должен быть
разрешён администратором MBusiness. Заголовки уведомления:

- X-Cashier-Event — идентификатор события.
- X-Cashier-Timestamp — Unix-время в секундах.
- X-Cashier-Signature — sha256=HEX HMAC-SHA256 от timestamp + '.' + RAW_BODY.

Проверьте подпись с вашим webhook-секретом по исходному телу, допустимость времени,
компанию, номер заказа, сумму и KZT. Пример реализации: `/docs#webhooks` и
`examples/verify-webhook.mjs`. Записывайте event_id и обновляйте заказ в одной
транзакции, чтобы повторная доставка не обрабатывала его второй раз.
Старое событие pending не должно отменять уже подтверждённый paid.

При необходимости запросите с привязанного сервера:

```sh
curl https://YOUR_MBUSINESS_SERVER/v1/invoices/INVOICE_UUID \
  -H 'Authorization: Bearer YOUR_API_KEY'
```

Заказ можно считать оплаченным только после paid с корректными данными.
Открытие ссылки, изображение QR и возврат покупателя из приложения не являются
подтверждением. При unknown нужна сверка; не создавайте второй счёт автоматически.

## 5. Обработайте ограничения и ошибки

- 401 UNAUTHORIZED — ключ неверен, отозван или заменён.
- 403 API_SERVER_REQUIRED / API_IP_NOT_ALLOWED — нет IP-привязки / другой сервер.
- 402 SUBSCRIPTION_REQUIRED — нет действующей подписки.
- 429 DAILY_LIMIT_REACHED — дневной лимит исчерпан по времени Asia/Almaty.
- 409 IDEMPOTENCY_CONFLICT — тот же заказ или ключ передан с другими параметрами.
- 409 AUTH_REQUIRED / LIVE_AUTOMATION_DISABLED — кассир не подключён / реальные операции выключены.

Повтор исходного запроса не расходует новое место в лимите. При отсутствии связи
повторяйте исходные параметры и ключ. Проверка статусов остаётся доступна после
окончания подписки, но IP-привязка обязательна и для чтения.

## 6. Проверка перед реальными заказами

Сначала пройдите sandbox-цикл: создание счёта → страница оплаты → имитация оплаты
→ webhook → обновление заказа в вашей системе. Затем отдельно проверьте вход и
полный цикл на реальном кассире с согласованным тестовым заказом.
Работоспособность прямого коннектора с текущим Kaspi пока не подтверждена.
