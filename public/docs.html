MBUSINESS / API V1

Одна интеграция.
Все платежи под контролем.

Создавайте счета из вашей CRM, интернет-магазина или приложения. Передавайте покупателю страницу оплаты и получайте подтверждение на свой backend.

Примеры используют YOUR_API_KEY и адрес вашего сервера. Банковская интеграция требует проверки на вашем кабинете. В sandbox денежные операции не выполняются.

Быстрый старт

  1. Зарегистрируйте компанию в MBusiness и сохраните секрет webhook. В «API и webhooks» укажите публичный исходящий IP backend-сервера, подтвердите паролем и сохраните новый API-ключ. Старый ключ отключится.
  2. Пополните баланс через подтверждённую администратором заявку и активируйте тариф.
  3. Подключите кассира через форму SMS-входа (в sandbox используется симулятор).
  4. С указанного сервера проверьте GET /v1/capabilities с Bearer-ключом. Затем создайте счёт и передайте checkout_url покупателю.
  5. Дождитесь статуса paid через API или подписанный webhook.
cURL · создание QR-счёта
curl -X POST https://YOUR_SERVER/v1/invoices \
  -H 'Authorization: Bearer YOUR_API_KEY' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: order-1001-attempt-1' \
  -d '{"order_id":"order-1001","amount":15000,"method":"qr"}'
Node.js ≥ 20
const response = await fetch(`${process.env.MBUSINESS_URL}/v1/invoices`, {

Авторизация

Все /v1/* endpoints требуют заголовок Authorization: Bearer YOUR_API_KEY. Ключ принадлежит одной компании. Храните его на сервере; не помещайте в браузер, Flutter или мобильное приложение. Ключ работает только с указанного исходящего IP сервера. До привязки запросы API запрещены. После ротации в кабинете старый ключ перестаёт работать немедленно, привязка к IP сохраняется.

Вход в MBusiness по логину и паролю и SMS-вход кассира Kaspi — отдельные действия. API не принимает SMS-коды и банковские сессии.

Привязка API к вашему серверу

  1. Узнайте постоянный публичный IP, с которого backend вашей системы выходит в интернет. При NAT это адрес внешнего шлюза, а не внутренний адрес контейнера.
  2. Откройте кабинет → «API и webhooks» → «Сервер интеграции». Укажите один IPv4 или IPv6 без порта, маски сети или URL. Подтвердите паролем MBusiness.
  3. Сохраните выданный новый ключ в секретах вашего backend. Старый ключ перестанет работать сразу, включая ключ, полученный при регистрации.
  4. Выполните пробный GET /v1/capabilities именно с этого сервера. Тест с рабочего компьютера или браузера может иметь другой IP и будет отклонён.
  5. Создавайте счета и принимайте webhook на вашем backend. Покупатели открывают checkout_url без API-ключа; их IP не ограничивается.
curl https://YOUR_SERVER/v1/capabilities \
  -H 'Authorization: Bearer YOUR_API_KEY'

Успешный ответ содержит api_server_ip — адрес привязки. Это подтверждает доступ API; не гарантирует, что банковский кассир подключён или реальные операции разрешены.

IP проверяется для всех /v1/*, включая чтение, тарифы и повторы запросов. Чужой адрес возвращает 403 API_IP_NOT_ALLOWED. Отсутствие привязки — 403 API_SERVER_REQUIRED. Ротация ключа сохраняет IP; смена IP выдаёт новый ключ и отключает предыдущий.

Разрешён один точный адрес. Если сервер выходит то по IPv4, то по IPv6, настройте постоянный адрес выхода. Динамический IP и смена NAT-шлюза требуют новой привязки. IP не доказывает физическую уникальность сервера: несколько машин за общим NAT или прокси имеют один адрес. Ключ всё равно должен оставаться секретом.

Не добавляйте X-Forwarded-For, X-Real-IP или Forwarded для обхода проверки. Их нельзя использовать как доказательство владения сервером. На стороне MBusiness адрес из X-Forwarded-For принимается только от явно настроенного доверенного reverse proxy, который заменяет заголовок реальным адресом клиента.

Создание счёта

POST/v1/invoices

Обязателен Idempotency-Key: 8–120 символов из букв, цифр, _, ., :, -. Повторяйте запрос с тем же ключом и теми же параметрами при потере ответа. Новый ключ для того же order_id не создаёт новый счёт.

ПолеТипОписание
order_idstringУникальный номер заказа компании, 1–100 символов. Буквы, цифры, _, ., :, -.
amountintegerСумма в целых тенге, от 1 до 99 999 999. Не в тиынах.
currencystringТолько KZT. Можно не указывать.
methodstringqr или phone.
customer_phonestringОбязателен для phone, формат +77001234567.
descriptionstringНеобязательное описание до 200 символов.

Ответ: 201 Created или 200 при повторе

  "amount": 15000,

Создание асинхронное. Передавайте checkout_url сразу: страница обновляет статус автоматически. payment_url и QR появятся после успешного ответа коннектора. Ссылка — это способ оплаты, а не доказательство списания денег.

Проверка статуса

GET/v1/invoices/:id

Возвращает счёт только вашей компании. Также доступны GET /v1/invoices (последние 100 счетов) и GET /v1/capabilities (режим и доступность методов).

СтатусЗначение
queued / processingВ очереди / выполняется запрос.
pendingОперация создана, ожидается оплата.
paidОплата подтверждена коннектором с проверкой данных операции.
declined / expiredОтказ / истечение операции.
unknownРезультат неизвестен. Не создавайте замену: требуется сверка.
failed / requires_authОшибка до отправки / кассиру требуется повторный вход.

Подтверждайте заказ только после paid и проверки merchant_id, order_id, amount и currency. При unknown не выставляйте повторный счёт автоматически.

Тарифы и дневной лимит

GET/v1/billing

Возвращает balance, plan, active, expires_at, used_today и remaining_today. Тарифы: Старт — 50/день за 10 000 ₸/мес; Бизнес — 200 за 25 000 ₸; Про — 400 за 60 000 ₸; Про Макс — 700 за 90 000 ₸. Больше 700 — по договорённости.

Подписка оплачивается с баланса за календарный месяц. Дополнительных 200 ₸ за счёт нет. Дневной лимит обновляется в 00:00 Asia/Almaty. Место резервируется атомарно при постановке в очередь, возвращается при подтверждённой ошибке до отправки. Неизвестная операция сохраняет место. Повтор исходного запроса места не занимает. Проверка ранее созданных счетов доступна и после окончания подписки.

Пополнение пока работает по заявке с ручной проверкой реального перевода администратором. Автоматический эквайринг не подключён. Регистрация не предоставляет бесплатного платного тарифа.

Webhooks

Задайте HTTPS-адрес в «API и webhooks». Администратор должен разрешить origin в WEBHOOK_ALLOWED_ORIGINS. Приватные адреса не допускаются. Сервис отправляет POST при изменении состояния счёта.

{
  "event_id": "EVENT_UUID",
  "type": "invoice.paid",
  "created_at": "2026-11-02T10:00:00.000Z",
  "invoice": {
    "id": "UUID", "merchant_id": "COMPANY_UUID",
    "order_id": "order-1001", "amount": 15000,
    "currency": "KZT", "status": "paid"
  }
}

Заголовки: X-Cashier-Event, X-Cashier-Timestamp (Unix seconds), X-Cashier-Signature: sha256=HEX. Подпись вычисляется как HMAC-SHA256(secret, timestamp + '.' + RAW_BODY). Важно использовать исходные байты тела, до повторной JSON-сериализации.

Node.js · проверка подписи
import { createHmac, timingSafeEqual } from 'node:crypto';

function verifyWebhook(rawBody, headers, secret) {
  const timestamp = headers['x-cashier-timestamp'];
  const supplied = headers['x-cashier-signature'];
  if (!/^\d+$/.test(timestamp || '')) return false;
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > 300) return false;
  if (!/^sha256=[0-9a-f]{64}$/.test(supplied || '')) return false;
  const expected = 'sha256=' + createHmac('sha256', secret)
    .update(timestamp + '.').update(rawBody).digest('hex');
  return timingSafeEqual(Buffer.from(expected), Buffer.from(supplied));
}

Повторная доставка возможна. Сохраняйте event_id и обрабатывайте его один раз в транзакции с обновлением заказа. События могут прийти не по порядку: не перезаписывайте подтверждённую оплату старым pending. При сомнениях получите текущее состояние через GET /v1/invoices/:id.

Отвечайте 2xx после надёжного сохранения события. Ошибки доставки повторяются до 12 попыток с увеличением задержки. Приостановленную доставку можно повторить из кабинета. При ротации webhook-секрета синхронно обновите обработчик.
