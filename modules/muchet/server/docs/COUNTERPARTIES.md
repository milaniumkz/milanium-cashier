# Карточка и взаиморасчёты контрагента

GET `/v1/companies/:companyId/counterparties/:kind/:id/statement`, kind=clients/suppliers. Права: catalog.read, accounting.read, documents.read, orders.read, debts.read, assets.read. Полный набор необходим, чтобы общая сводка не скрывала часть доступных категорий молча. Для ограниченных сотрудников сохранён отдельный `/service-statement` с catalog.read/documents.read/accounting.read. Владелец переключает состав в карточке. Ни один вариант не изменяет учёт.

Общий регистр объединяет устойчивые ссылки commercial_postings/payments, order_postings/payments/settlement_postings, debt_postings и asset_postings. Строка журнала входит один раз; старые проводки, отмены и пересчёты сохраняются и суммируются. Отсутствие active-фильтра намеренно: исключение обратных проводок исказило бы итог. Оплаты счёта, перенесённые в проведённый акт, не учитываются повторно.

Возвращаются счета receivables/customer_advances для клиента и payables/supplier_advances для поставщика, начальное сальдо, дебет/кредит периода, конечное сальдо; движения с source_kind/source_id, датой, проектом, строками и nextCursor. Параметры from/to, scope ACCOUNTING или MANAGEMENT (включая записи BOTH), projectId или unassigned, limit/after. Итоги рассчитываются по всему фильтру, независимо от страницы. Суммирование PostgreSQL NUMERIC с проверкой безопасного диапазона API, без float. Заголовок и движения читаются в едином REPEATABLE READ снимке; это также применено к отдельной сверке услуг.

Карточка открывает основание в рабочем редакторе соответствующего модуля. Раздел документов ниже отдельно показывает счета/акты услуг; остальные основания доступны через движения. Ручные проводки без связи с контрагентом, неоднозначные старые источники и несуществующий пока модуль закупки товаров не подменяются выдуманными данными. coverage=LINKED_JOURNAL_ONLY и пояснение в UI явно ограничивают состав. Это внутренний регистр, не подписанный акт сверки и не налоговая форма.

Проверено на реальной БД: услуги + товары + начальный долг, авансы, отмены, исправления после закрытия, перенос продажи между проектами/датами, приобретение и изменение стоимости ОС, пагинация, полномочия и границы компаний. Живой Flutter-сценарий проверяет открытие основания и переключение состава; реальная резервная копия восстанавливает суммы клиента/поставщика из всех этих источников.
