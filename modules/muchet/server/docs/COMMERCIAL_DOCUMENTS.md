# Документы услуг

Все маршруты ниже внутри `/v1/companies/:companyId`. Список возвращает summary по всему фильтру (count, drafts, outstanding), независимо от пагинации. Неоплаченная сумма исключает повтор задолженности по счёту с проведённым актом. Доступ проверяется по membership компании, суммы передаются целыми минимальными единицами KZT. Количество услуги — десятичная строка до трёх знаков. Расчёт выполняет сервер через BigInt с округлением половины вверх; клиент показывает серверный результат.

| Маршрут | Назначение | Право |
|---|---|---|
| GET /commercial-documents | Поиск/фильтры/пагинация | documents.read |
| POST /commercial-documents; PUT /commercial-documents/:id | Создание/версионное изменение | documents.write |
| POST /commercial-documents/preview | Расчёт без сохранения | documents.write |
| GET /commercial-documents/:id | Суммы, оплаты, остаток, переплата | documents.read |
| POST /commercial-documents/:id/post | Выставить счёт/провести акт | documents.post |
| POST /commercial-documents/:id/cancel; /post | Отмена/восстановление | documents.post |
| POST /commercial-documents/:id/act | Акт из счёта | documents.write |
| GET /commercial-documents/:id/payments | Связанные оплаты | documents.read |
| POST /commercial-documents/:id/payments | Оплата или возврат денег | documents.settle + wallets.transact |
| PUT /commercial-documents/:id/payments/:paymentId | Изменить оплату/возврат | documents.settle + wallets.transact |
| POST /commercial-documents/:id/payments/:paymentId/void; /restore | Отменить/восстановить запись | documents.settle + wallets.transact |
| GET /commercial-documents/:id/movements; /history | Проводки и история | documents.read |
| GET /commercial-documents/:id/export-data; /print | Данные PDF / HTML печать | documents.export |
| GET /commercial-documents/:id/files | Приватные вложения | documents.read + files.read |
| POST /commercial-documents/:id/files | Привязать загруженный файл | documents.write + files.read |

Изменяющие команды требуют Idempotency-Key. Клиент сохраняет исходный payload и ключ при неизвестном результате сети. PUT документа требует текущую version. Изменение проведённого документа дополнительно требует documents.post. Запрета по месяцу или возрасту документа нет.

## Финансовая модель

Счёт сам по себе не признаёт доход. Оплата до акта учитывается как аванс. Акт признаёт дебиторскую задолженность/доход (или расход/кредиторскую задолженность для покупки), затем зачитывает авансы. Один счёт имеет один связанный акт; повтор преобразования возвращает существующий. Счёт и связанный акт используют общую группу оплат и возвратов, в том числе после отмены/восстановления акта. У счёта с проведённым актом нет повторного остатка к оплате. Переплата возникает на дату фактического платежа; зачёт предоплаты — на дату признания акта. Изменение проекта черновика акта не переносит платежи счёта до проведения.

Изменение проведённого документа сторнирует действующие начисления и формирует исправленные движения. Денежные остатки синхронизируются с нормализованной двойной записью. Переплата сохраняется как обязательство перед клиентом, не изображается возвратом денег. Отмена записи оплаты исправляет ошибочную запись. Настоящий возврат денег создаётся отдельным событием REFUND в том же регистре денежных операций; он уменьшает аванс, затем при необходимости открывает долг. Сам возврат денег не изменяет стоимость услуг, выручку/расход или НДС: для этого исправляют исходный акт. Прямое финансовое изменение проводки документа направляет пользователя к основанию, чтобы не рассогласовать регистры; это не временный запрет редактирования.

Проект задаётся документу. Его исправление меняет аналитику документа и связанных платежей, общая сумма фирмы не удваивается. Юридические реквизиты, налоговая регистрация и файлы принадлежат фирме; чужие ссылки отвергаются.

## Правовые границы

Явная стандартная ставка16% поддерживается для2026 по статье503 Налогового кодекса РК. Нулевая ставка и необлагаемые операции не объявляются автоматически законными: для зарегистрированного плательщика требуется основание. Льготы, место реализации и право на зачет не определяются одним переключателем. НДС покупки можно включить в стоимость или выделить как PENDING до проверки права на зачет. Налоговая отчётность, ЭСФ и фискальные чеки не формируются.

Реквизиты сохраняются снимком на дату ввода документа. Явное обновление снимка и любые последующие правки доступны с историей. PDF/HTML — внутренний печатный шаблон; подписи пустые, подписание не имитируется, утвержденная форма Р-1 пока не реализована.

Товарная продажа проходит отдельный FIFO-процесс. Товарная закупка с PURCHASE_GOODS использует этот редактор с явным выбором товара/склада и подключённым источником партий; детали в [PURCHASES.md](PURCHASES.md). Документ PURCHASE_ACT по-прежнему относится к услугам и не создаёт складской остаток.

## Карточка контрагента и сверка услуг

GET `/counterparties/:kind/:id/service-statement` (kind=clients/suppliers) требует catalog.read, documents.read и accounting.read. Период from/to, scope=ACCOUNTING/MANAGEMENT (BOTH входит в каждый отчёт один раз), projectId либо unassigned. Остатки считаются по связанным проводкам receivables/customer_advances либо payables/supplier_advances. Учитываются исходные записи, сторно, отмены и восстановления оплаты; счёт и акт не создают повторного долга. Оплаты счёта относятся к проведённому акту, если он есть. Это сводка услуг; начальные долги, товары и ОС пока не включены. Независимый cursor пагинирует движения по дате/id, не меняя итоги. Поля opening/closing — дебетовое сальдо, поэтому кредитовые авансы покупателей и долг поставщику отрицательны в API; UI показывает естественный знак соответствующего счёта.

Список commercial-documents дополнительно принимает точный counterpartyId и scope. Карточка открывает документы и основания движений. Исправления исходного документа пересчитывают текущие расчёты, в том числе закрытого периода; это текущая исправленная история, а не неизменяемый снимок ранее сданной отчётности.

Список поддерживает status=DRAFT/ISSUED/POSTED/CANCELLED вместе с направлением, типом, проектом, контуром, контрагентом, поиском и диапазоном дат. Неизвестный статус отклоняется. Строки, оплаты и summary читаются в одном снимке PostgreSQL. В интерфейсе продаж/покупок фильтр «Все статусы» применяет серверный отбор, включая итоговые карточки; тип документа и контур сохраняются.

## Возврат денег и история операции — схема24

POST `/commercial-documents/:id/payments`: `kind=PAYMENT` (по умолчанию) или `REFUND`, положительные целые `amount`, `walletId`, `businessDate`. Для продажи REFUND списывает деньги клиенту; для покупки зачисляет возврат поставщика. Возврат доступен и после отмены документа, если реальные деньги ещё остаются у фирмы/поставщика. Он не означает возврат товара, корректировочный ЭСФ или банковское перечисление вне приложения.

Денежные события упорядочены по календарной дате. В одну дату сначала признаётся акт, затем оплаты, затем возвраты; время внутри дня не моделируется. Возврат не может превышать накопленную сумму оплат за вычетом предыдущих возвратов на эту дату. Исправление/отмена оплаты, которая уже обеспечила возврат, требует сначала согласовать возврат; вся неудачная команда откатывается. Это проверка реального денежного остатка, а не запрет редактирования по возрасту или периоду. Суммы считаются в минимальных единицах через BigInt.

PUT/void/restore сохраняют аудит; записи имеют version, новый интерфейс передаёт её для защиты от устаревшего редактирования. Для совместимости старого клиента version у этих маршрутов пока необязательна. Вид PAYMENT/REFUND существующей записи не меняется: ошибочную запись отменяют и вводят правильную. GET `/:id/payments/:paymentId/history` возвращает текущую запись и до200 предыдущих снимков с автором. Карточка операции открывает эту историю, позволяет исправить, отменить и восстановить запись; доступ читателя ограничен серверными правами.

Выписка сопоставляется с введённым возвратом через EXISTING без повторного движения денег. Отмена помечает связь PAYMENT_VOIDED, правка суммы/даты — SOURCE_CHANGED. Служебные записи отмены/восстановления не предлагаются как дополнительные платежи. Если возврат ещё не введён, классификация DOCUMENT_REFUND создаёт его при подтверждённом проведении строки через ту же команду расчётов: исходящий возврат выбирает продажу, входящий — покупку, в том числе отменённую. Повтор проведения не создаёт второй возврат. В интерфейсе вариант называется «Возврат денег по документу»; DOCUMENT остаётся обычной оплатой.
