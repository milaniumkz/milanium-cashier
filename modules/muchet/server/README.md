# Независимый M-учёт API: текущий проверенный этап

Node.js **24.x**, Fastify 5 (модульный JavaScript), **PostgreSQL 17**. SQLite больше не используется. Требования пользователя: [полное задание](../docs/requirements/2026-10-20.md). Это техническое ядро, **не завершённая бухгалтерская система Казахстана**. Новый Flutter REST workspace подключён, исходные экраны ещё переносятся; юридические расчёты и официальные формы не утверждены.

## Запуск из корня репозитория

```bash
make bootstrap
make up
make seed-dev
make test
make test-e2e
make backup-test
```

`make bootstrap` сохраняет существующий .env либо создаёт приватные настройки с новым случайным паролем локальной БД; устанавливает зависимости по lockfile. `make up` запускает настоящий PostgreSQL в Docker Compose, применяет SQL-миграции и поднимает API на 127.0.0.1:8080. Данные PostgreSQL хранятся в именованном Docker volume, файлы — в DATA_DIR. `make down` останавливает только API, запущенный task runner, и сохраняет данные. Команды не вызывают docker compose down -v и не удаляют пользовательские данные.

`make seed-dev` работает только при APP_ENV=development; создаёт явно синтетического владельца и компанию. Случайный тестовый пароль сохраняется с правами 0600 в игнорируемом `.runtime/synthetic-login.json`, не выводится в консоль и не попадает в Git. Повторный seed сохраняет существующие реквизиты. Это не production bootstrap. Публичная регистрация по умолчанию выключена.

`GET /health` проверяет запрос БД и возвращает status=ok/schemaVersion=21. `GET /openapi.json` описывает зарегистрированные маршруты; экспорт: `cd server && npm run openapi`. Схемы тел OpenAPI пока неполны; детальное описание исходного API: [docs/API.md](docs/API.md), расширения перечислены ниже. Не генерируйте production-клиент из неполных схем.

## Реальные возможности

- Авторизация с scrypt, bearer-сессии на 12 часов, хеш токена в БД, отзыв сессии и всех сессий при смене пароля. Членство и явные права на каждую организацию. Владелец одной организации не получает доступ к другой.
- JSON-справочники по allowlist с optimistic locking; приватные файлы до 10 MiB. Финансовые регистры и security-коллекции не открываются произвольным CRUD.
- FIFO-партии, приход, резерв, отмена, отгрузка, себестоимость, оплаты заказов; перемещения и списания свободного остатка. Отрицательные складские остатки запрещены.
- Кошельки: начальный капитал, доход/расход, переводы, история; входящие/исходящие долги, частичные погашения и история. Кассовые смены с фиксацией пересчёта. Это внутренний учёт, не фискальная ККМ.
- Журнал двойной записи, точные NUMERIC-строки в PostgreSQL, deferred-проверка баланса на уровне БД, редактирование проведённых записей с историей версий и связанное сторно ручной записи. Сторно складских и денежных операций отдельными бизнес-командами ещё не реализовано.
- Контуры ACCOUNTING/MANAGEMENT/BOTH, оборотная ведомость, внутренний P&L с датами. Отметки закрытия/открытия периода; по последнему указанию владельца они не блокируют редактирование. Бизнес-дата по часовому поясу компании (по умолчанию Asia/Almaty), хранится отдельно от UTC timestamp.
- Идемпотентность финансовых команд, блокировка строки компании в PostgreSQL, атомарные проводки/остатки/аудит/сохранение ответа. Проверка конкурентных запросов из двух API instances.
- Очередь внутренних команд устройств LOCK/UNLOCK/SYNC и подтверждение оператором. Это не подключение к реальному устройству: device authentication и агент ещё нужны.

Деньги в API — **целые minor units**, в БД — NUMERIC(20,0), суммы строк журнала — отдельные NUMERIC-поля. 100 = 1.00 KZT. Количество — целые базовые единицы товара. Дробные единицы требуют явного масштаба и клиентского преобразования, которые ещё не реализованы. Лимит отдельных величин 10^12, проверяются safe integer и переполнения. Код счетов пока внутренний, а не утверждённый типовой план счетов Казахстана.

## Проверки и восстановление

`make test` проверяет 41 серверный сценарий на PostgreSQL, `make test-e2e` — реальный HTTP с перезапуском, `make backup-test` — реальный pg_dump/pg_restore в отдельную временную БД и восстановление приватного файла. Тесты используют отдельные случайные test_* схемы и синтетические данные. Backup-test ограничен локальным Compose PostgreSQL. API health не заменяет эти проверки.

`cd server && npm run backup` создаёт закрытый development pg_dump в .runtime/backups. Файлы uploads копируются отдельно при остановленном API. Backup-test проверяет именно такую согласованную остановленную копию, не заявляет online-consistency двух независимых хранилищ. Для production нужны отдельное расписание, шифрование, удалённое хранение, политика сроков хранения и повторный restore-test на целевом сервере.

`make lint-server` проверяет синтаксис Node. Общий `make lint` дополнительно требует Flutter analyze. `make verify-no-firebase` намеренно завершается с ошибкой, пока старые активные зависимости остаются. `make verify` запускает обязательные проверки и не считается успешным при недоступном Flutter.

## Редактирование

Последнее указание владельца и реализация: [изменение требований](../docs/requirements/2026-10-20-editing.md). `PUT /wallets/:id` принимает name/balance, `PUT /accounting/journal/:id` — description/lines/scope/businessDate/reason, `PUT /orders/:id` — items/scope/businessDate. Все эти команды требуют Idempotency-Key. Права: wallets.write (и wallets.transact для баланса), accounting.edit и orders.edit соответственно. История: GET /accounting/journal/:id/history и GET /orders/:id/history. CLOSED не блокирует редактирование. Необходимые остатки и баланс проводок всё равно проверяются.


## Динамические проекты

Все маршруты ниже внутри `/v1/companies/:companyId`; права и компания проверяются сервером.

- `GET /projects`, `POST /projects {name,description?}` — projects.read / projects.write.
- `PUT /projects/:id {version,name?,description?,archived?}` — версия обязательна, история сохраняется; projects.write.
- `GET /reports/projects?projectId=...&from=YYYY-MM-DD&to=YYYY-MM-DD&scope=ACCOUNTING` — reports.read. Без projectId все проекты плюс общие операции; `unassigned` означает общие операции. `total` всегда общий итог фирмы за выбранный период/контур, `items` учитывает фильтр проекта.
- `projectId` (или null для общих операций) поддерживается в создании/правке сделок, ручных проводках и денежных доходах/расходах. Отгрузка, себестоимость и оплата наследуют проект сделки. Перенос оплаченной сделки пересчитывает обе аналитики, сохраняя итог фирмы.
- Налоговый контур фирмы общий. Автоматического распределения общих расходов нет. Архивирование не удаляет проводки и не запрещает исправление прежних операций.

Новый интерфейс запускается как основной main.dart или явно: `scripts/flutter.sh run --target lib/main_server.dart --dart-define=API_ORIGIN=http://127.0.0.1:8080` (для отдельного web dev origin задайте точный CORS_ORIGIN на API). Предпочтительно собрать `make build-workspace-web` и обслуживать web через WEB_ROOT на самом API: same-origin и локальный CanvasKit, без внешнего CDN. Полная миграция всех функций не завершена.


## Общие параметры фирмы и правка денежных операций

`GET /settings` (organization.read), `PUT /settings` (organization.write, Idempotency-Key) сохраняют legalName, identifier (null или12 цифр), legalForm TOO/IP, taxRegime GENERAL/SIMPLIFIED, vatRegistered и обязательную version. Настройки общие для фирмы; выбор режима не является проверкой налоговой применимости, налоговые формулы из этих полей пока не выполняются.

`PUT /wallets/:id/entries/:entryId` (wallets.transact, Idempotency-Key) изменяет сумму, INCOME/EXPENSE/CAPITAL, описание, проект и businessDate связанной операции. Проводка сохраняет id и историю, пересчитываются остаток и прибыль. Денежные счета теперь согласуются с журналом и при ручном проведении/правке; для ручных wallet:* строк дополнительно требуется wallets.transact. Старые development-записи без связи journal_id требуют сверки вместо угадывания соответствующей проводки. Правка переводов и погашений долгов отдельными командами пока не реализована; правка одной строки не подменяет изменение всей связанной операции.

`GET /wallets/:id/entries` поддерживает projectId (или unassigned), after, limit; возвращает описание, дату, проект и nextCursor. Новый UI показывает операции и позволяет редактировать связанные доходы/расходы.


## Первый владелец на чистой установке

Публичная регистрация по умолчанию закрыта. Для реальной установки не запускайте `seed-dev`: он предназначен только для синтетической локальной проверки.

После настройки DATABASE_URL и миграций выполните из `server/`:

```sh
npm run provision-owner < /secure/path/initial-owner.json
```

Входной JSON содержит `login`, `name`, `password` (12–256 символов). Создайте файл вне репозитория с правами 0600 или передайте JSON через stdin из менеджера секретов. Не вводите пароль в аргументы командной строки и не коммитьте его. Команда не печатает credentials, хранит scrypt-хеш и отказывает, если существует хотя бы один пользователь. Конкурентные запуски создают только одного владельца. Это не механизм сброса чужого пароля.

После входа новый интерфейс предлагает создать фирму. Создание фирмы поддерживает Idempotency-Key, повтор запроса не создаёт вторую фирму; ключ принадлежит текущему пользователю. Реквизиты и налоговый режим вводятся в настройках фирмы, проекты создаются с произвольными названиями.

## Выписки, отчёты, склад и восстановление доступа

Банковский импорт принимает CSV UTF-8 (до750КБ/500операций), поддерживает настраиваемые названия колонок и разделитель. Сначала выполняются предварительная проверка и загрузка без проводок; затем оператор явно выбирает доход/расход/вклад/документ/не проводить и подтверждает каждую строку. Уникальный ID банковской операции проверяется в пределах фирмы и денежного счёта. Повтор не создаёт движение; тот же ID с другими данными отклоняется. Номер платёжного поручения, повторяемый банком, не подходит в качестве уникального ID. Автоматическое распознавание всех банковских форматов и сверка начального/конечного остатка выписки ещё не реализованы.

Оплата счёта/акта из выписки использует общий сервис расчётов документов. После проведения исходная строка выписки остаётся свидетельством импорта; исправление открывает связанную денежную операцию или документ, сохраняет историю и пересчитывает баланс. Проводки не создаются повторно при перезагрузке страницы.

Финансовые отчёты поддерживают период, проект, бухгалтерский/управленческий контур. ОСВ содержит начало/дебет/кредит/конец. Из счёта открывается журнал за тот же фильтр, затем основание. Ручная запись редактируется с историей и проверкой revision; изменения проведённых коммерческих документов выполняются через основание. CSV защищает текст от формул электронных таблиц. Статусы месяцев не блокируют исправления и не означают выполнение всех регламентных процедур.

Складской экран показывает FIFO-партии, резерв и доступное количество. Поступление/перемещение/списание используют серверные команды и Idempotency-Key. Количество пока целое в явно выбранной базовой единице; самостоятельный приём дробного количества и средневзвешенная оценка не заявляются реализованными.

Для восстановления пароля администратор сервера выполняет из `server/`:

```sh
npm run issue-recovery -- --login user@example.test --output /secure/path/recovery.json
```

Выходной файл должен быть новым, путь — приватным. Команда создаёт файл0600 и не печатает код. Код действует15минут, хранится в БД только в виде SHA256, применяется один раз. В форме «Забыли пароль?» пользователь вводит полученный код и новый пароль; старые сессии отзываются. Это офлайн-восстановление через администратора, email-доставка пока не подключена; письма не отправлялись.

Карта фактической реализации38макетов: `docs/design/implementation-status.json`. Она отличает работающий сценарий от полного соответствия макету. Актуальные версии схемы, проверки и незавершённые части — в `docs/CHECKPOINT.md`; описание начальных долгов — в `docs/DEBTS.md`.


## Активы и сотрудники

Схема14 добавляет `/assets` и `/employees` внутри фирмы. Права assets.read/write/post и employees.read/write выдаются отдельно. Кадровые данные не читаются через organization.read или универсальный `/resources/employees`.

Активы поддерживают черновик, ввод в эксплуатацию, выбранную линейную амортизацию по полным месяцам, исправление исходных данных, списание и восстановление с проводками/историей. Политика `OWNER_LINEAR_MONTHLY_V1` распределяет целые минимальные денежные единицы накопительным округлением; это бухгалтерская модель выбранных параметров, не автоматическое определение применимости НСФО/МСФО или налогового вычета. Пересмотр оценок на будущее, модернизация и реализация актива ещё не реализованы. При исправлении проекта сторно остаётся в прежнем проекте, новые движения относятся к новому — общая сумма не удваивается.

Сотрудники имеют отдельные версии и историю, серверный поиск, даты приёма/увольнения, текущий оклад, основной проект затрат и сведения для будущего расчёта. Оклад не формирует зарплатную проводку сам по себе. Зарплатные начисления и официальная200.00 ещё не заявляются готовыми.

В живых сценариях проверены склад и реестры на mobile390×844, редактирование сумм в закрытом месяце и восстановление пароля. Для выборочного живого прогона: `cd server && APP_ENV=test node --env-file=../.env scripts/client-e2e.mjs test_live/assets_workspace_test.dart`.

Внутренние отчёты фирмы и проектов теперь классифицируют известные конечные числовые счета справочника2026:6xxx как доходы (дебет6020/6030 уменьшает доход),7010 как себестоимость, остальные7xxx как расходы. Служебные имена счетов документов поддерживаются одновременно. Суммы агрегируются точно через BigInt и проверяются перед выдачей. Используется единая классификация обоих отчётов. Это внутренняя сводка по справочнику2026, не утверждённая форма финансовой отчётности: неизвестные пользовательские счета и группы автоматически не интерпретируются; классификация иных редакций плана счетов не заявляется. Числовые1010/1030 не подменяют привязку к конкретному денежному счёту и не изменяют его регистр автоматически. Полная числовая политика автоматических проводок ещё не завершена.

Календарь и подготовка фирмы (schema21): [TAX_CALENDAR.md](docs/TAX_CALENDAR.md). Сохранение проверок профиля/документов, ручные задачи со сроком, статусом, основанием и историей. Автоматические официальные сроки ещё не загружены.

Общий поиск фирмы по документам, контрагентам, товарам, сотрудникам, проектам и ОС: [SEARCH.md](docs/SEARCH.md). Сервер ограничивает категории правами, открытие карточки повторно проверяет доступ. Production-журнал исключает query-string и приватные детали внутренних ошибок.

Сводка доходов уточнена: `salesRevenue` — продажи (6010 с уменьшением на6020/6030 и служебный revenue), `otherIncome` — остальные известные конечные6xxx, `revenue` — все доходы, `grossProfit` — только продажи минус себестоимость, `netProfit` — все доходы минус себестоимость и расходы. `costs` рассчитывает сервер. `/reports/projects` возвращает `total` всей фирмы и `selectionTotal` выбранного проекта/общих операций; клиент использует готовые итоги. Это внутренний отчёт по справочнику2026, не утверждённая форма финансовой отчётности.

Общие взаиморасчёты клиента/поставщика по услугам, товарным продажам, начальным долгам и ОС: [COUNTERPARTIES.md](docs/COUNTERPARTIES.md). Состав зависит от явно проверенных полномочий; несвязанные ручные и старые источники требуют сверки.

Остатки и пересчёты (schema23): [docs/INVENTORY.md](docs/INVENTORY.md). Сводка по всем выбранным партиям, минимумы, CSV; физический пересчёт с версиями, атомарным FIFO-списанием/подтверждённым излишком, исправлениями и историей. Налоговая квалификация и официальная форма автоматически не заявляются.

Денежные возвраты по услугам: возврат клиенту/от поставщика, дата фактических денег, исправление, отмена/восстановление и история с автором. В банковской выписке можно создать возврат по документу либо сопоставить уже учтённый. Стоимость услуги и НДС изменяются через акт: [модель и API](docs/COMMERCIAL_DOCUMENTS.md).

Товарные закупки: черновик, предоплата до поставки, проведение в FIFO и долг поставщику, НДС в стоимости/к проверке, исправления, оплаты/денежные возвраты, сверка и переход из партии к основанию. Границы пересчёта использованного запаса и физических возвратов: [товарные закупки](docs/PURCHASES.md).

Товарные возвраты поставщику: отдельные исправляемые документы, исходные FIFO-партии, датированное уменьшение долга/требование к поставщику, отдельный возврат денег, история, поиск и внутренний PDF. API и границы: [PURCHASE_RETURNS.md](docs/PURCHASE_RETURNS.md).
